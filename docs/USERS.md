# User management API and Redux

Server record and write types live in `src/server/schema/users_schema.ts`. Frontend components and Redux use `src/types/users.ts`. These are separate contracts; neither file imports the other.

Express exposes `GET /api/users`, `GET /api/users/options`, `GET /api/users/filter-options`, `POST /api/users`, and `POST /api/users/:id/assignments`. All require a verified session and the matching `users` permission. Responses use private, no-store caching. Creation requires the application's Origin and is rate limited.

List query parameters: `page` (default 1), `page_size` (default 10; allowed values 10, 20, 50, 100), `search` (case-insensitive name or email search). Response: `{ users, total, page, page_size }`; every user includes the required `name`. Options return `{ companies, roles }`; roles have company scope only.

Creation requires `{ name, email, password }`. Super Admin may also send optional `company_id` and `role_ids`. A company supervisor must send `company_id`, `page_keys`, and either `role_name` or `role_id` (the Users page is rejected). A new role name becomes a unique slug. `role_id` reuses a role that already belongs to that company and does not include Users. A name must contain 1–250 characters. Omit both assignment fields to create an account without a company or roles. Providing a company alone creates a membership without roles. `role_ids` can be omitted or empty for Super Admin; nonempty roles require `company_id` and must be distinct company-scoped roles (maximum 50). Omit unused fields rather than sending null or an empty company ID. The backend trims the name, normalizes email, validates supplied assignments, creates an email-confirmed Supabase account with display-name metadata, and saves the database profile and optional membership with roles in a transaction. No global roles, invitation email or forced password-change flow. Configure backend-only `SUPABASE_SECRET_KEY` on the API service. The seed saves `SEED_SUPER_ADMIN_FULL_NAME` in the profile and metadata, defaulting to `Super Admin`. Login requires an existing admin-provisioned profile and preserves its name; neither password nor Google login creates missing profiles.

Auth and Postgres cannot share a transaction. Failed persistence triggers deletion of only the newly created Auth account. Failed cleanup logs its account UUID for operator reconciliation without credentials. A process interruption between the two systems can also leave an account requiring reconciliation. Duplicate accounts return 409; existing accounts are never modified or adopted.

Redux exports `listUser(query)`, `getUserOption()`, `createUser(input)`, `resetUsers()`, `clearCreateStatus()` and `selectUser` from `src/lib/store/users-slice.ts`. List, options and creation have separate statuses/errors. Errors retain HTTP status for redirecting on 401 or showing access denied on 403. List/options ignore older responses and support cancellation.

`CreateUserInput`, `CreateUserResponse` and `UserSummary` share the required name through the backend and Redux. A company supervisor also sends `company_id`, `page_keys`, and either `role_name` or `role_id`. Super Admin omits `page_keys`, so the membership stays on `role_pages`. Login and session responses use the saved profile name. Accounts without a database profile are rejected before the session response is served. Swagger documents these request and response fields.

Keep form values local. `createUser` uses a manual thunk to keep passwords absent from dispatched plain actions and Redux state. Await `dispatch(createUser(input))` directly; it returns the created user or rejects with `{ status, message }`. Fetch thunks support `.unwrap()`. After successful creation, dispatch `listUser(currentQuery)` to refresh the current filter/page. Creation invalidates in-flight list results. Reset users on sign-out and abort pending reads when leaving the page.

Apply the `user_company_pages` migration before using staff dashboard checks. Configure Supabase/Postgres, apply migrations, seed a super-admin, and ensure companies and company roles exist for real creation. Live database/Auth integration must be verified separately. The Users UI includes search, table/card views, shared pagination and a creation dialog. Super Admin enters name, email, and password, then assigns a company and roles. A company supervisor also chooses the staff role and dashboards, with the company locked to their own. Success closes the dialog and refreshes the first page; errors keep form values for retry. `/roles` and `/companies` require the global `super_admin` role at the page proxy. `/users` also opens for a company user whose session includes the Users page. The users API checks `users.view`, `users.add`, and `users.edit`. Super-admin sidebar navigation includes all registered dashboard pages without explicit page/permission grants. Ordinary users retain grant-based navigation and the authenticated dashboard home.

Company supervisors creating staff are described in [Company supervisors and staff](COMPANY_STAFF.md). Their checks use `assigned_pages` on that membership. View, add, edit, delete, and All / My company / Only me stay on the role.

The Users repository exports named async functions: `list_user`, `get_user_filter_data`, `get_user_option`, `assignable_user`, and `create_user`. List snapshots and user creation retain their database transactions.

The Users service exports named async functions: `list_user`, `get_user_option`, `get_user_filter_option`, and `create_user`. Repository and Auth dependencies can be supplied directly to these functions for tests; no service factory or service object is exported.
