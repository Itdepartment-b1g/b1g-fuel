# Authentication and access control

Supabase Auth handles passwords and verifies users. Express uses `@supabase/ssr` to read/write session cookies and `auth.getUser()` to validate every protected request. Sessions are refreshed via response cookies. Cookies are HttpOnly, SameSite=Lax, and Secure in production. The browser talks to the frontend host through the `/api` proxy.

`src/server/security/jwt.ts` centralizes verification as `verifyUserToken(auth, token?)`. Without an explicit token, it verifies the cookie-managed access token through the SSR client's `getUser()` and retains its refresh behavior. With a raw Supabase JWT, it rejects malformed token strings and asks the configured Supabase Auth server to verify the token. It returns a verified User or a safe 401 application error; it never logs tokens or trusts decoded payloads. Supabase issues/signs the access tokens, so no separate app JWT secret is needed. [Supabase verification reference](https://supabase.com/docs/reference/javascript/auth-getuser)

`authService.requireUserAccess` and the Google callback service use this helper, then separately enforce existing Prisma profiles. Database role assignments determine administrative access; JWT metadata does not grant `super_admin`. Browser login remains cookie-based and returns identity rather than access tokens. This helper does not add HTTP Bearer authentication to the routers.

Apply `requireAuthUser` to future protected resource routers. It verifies the Auth user and requires an existing Prisma profile matching the Auth UUID; missing profiles are rejected with 403 and the browser session is cleared. For per-user data, constrain every repository query by the verified session owner. Profiles are provisioned by the seed or protected user-creation API. Password and Google login never create missing profiles. See [Google login](GOOGLE_AUTH.md) for the OAuth flow.

Prisma uses a trusted Postgres connection; **application authorization must be enforced regardless of Supabase RLS**. The initial migration enables RLS with no public policies to prevent unintentional access via Supabase's browser Data API. Use a trusted backend database role for Prisma. If you intentionally expose data through PostgREST later, add explicit policies rather than disabling RLS.

`src/server/security/middleware.ts` owns `getAppOrigin` and `createOriginMiddleware`. APP_ORIGIN must be an HTTP(S) origin with no credentials, path, query or fragment; it is canonicalized for request checks and Google OAuth redirects. Invalid configuration prevents API creation. Mutation requests require that exact Origin, including scheme and port. Requests supplying another Origin are rejected with 403. Reads without Origin remain available for server requests and OAuth callbacks. Scripts making mutations must supply the application Origin; authentication is checked separately.

Allowed-origin responses include an exact `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true`, and `Vary: Origin`. Preflights for GET/HEAD/POST/PATCH/DELETE/OPTIONS and Content-Type are answered with 204; unsupported methods or requested headers are rejected. Middleware runs before body parsing and resource routers. Next.js still forwards browser Origin/Cookie headers through the same-origin API proxy. CORS headers control browser response access; mutation Origin validation provides the application's CSRF protection. [CORS reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

`API_HOST`, `API_PORT` and `createApp().listen(...)` remain in `src/server/index.ts`: they bind/start the service once, while middleware handles individual requests. Change APP_ORIGIN/API binding environment values before starting or restarting the API. Auth attempts are rate limited per connecting IP with an in-memory limiter. Behind the default Next.js proxy that IP can be shared; configure trusted proxy topology and a distributed limiter before scaling to multiple API instances.

Never expose `DATABASE_URL` or a Supabase service-role key to the client. `.env` is ignored; `.env.example` contains placeholders. Unexpected failures are logged only on the API service and return generic messages. Request bodies are limited to 16 KB. Serve the production frontend over HTTPS and keep Express behind a trusted proxy or private network.

`SUPABASE_SECRET_KEY` is used by the explicit super-admin seed and backend user creation. `prisma/seed.ts` never logs credentials and preserves the password when reusing an existing confirmed account. Global role assignments live in Postgres, rather than editable user metadata. `/api/auth/session` verifies the Supabase user, returns that user's global role slugs, and uses `private, no-store` caching. Next.js `src/proxy.ts` checks that endpoint before serving `/dashboard`, `/users`, `/roles` and `/companies`, and forwards refreshed or cleared session cookies. Management pages require the verified global `super_admin` role; ordinary users are redirected to Dashboard. The users API requires the global `super_admin` role for listing, creation and company/role options. Other administrative endpoints must enforce authorization independently. See [User management](USERS.md) for creation, cleanup and Redux behavior.

For a new resource, decide whether it is public, shared/authenticated, or per-user. Add auth middleware when protected; scope all per-user repository methods; use included credentials in client requests; document endpoints; verify unauthenticated rejection and cross-user isolation.
